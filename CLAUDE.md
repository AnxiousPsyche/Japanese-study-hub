# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"JP Library OS" — a static, no-build multi-page site that teaches Japanese (JLPT N5/N4) through a retro "desktop OS" shell. There is no `package.json`, no bundler, no test runner, and no linter configured. Everything is hand-written HTML/CSS/vanilla JS loaded directly via `<script src>`/`<link>` tags.

The Adventure Room is a Phaser 3 mini-game (a walkable pixel-art library) that replaces flat lesson lists with an explorable map, and was the most actively developed piece for a long stretch — most of that work lives in a single large file, `assets/js/n5-phaser-game.js`. More recent sessions have shifted focus to the document-mode Study Room, Kana Dojo, and the N5 Kanji card-gallery track instead (see below) — don't assume the Phaser game is still where new work is happening without checking recent commits.

## Commands

There is no build/lint/test tooling. To run the site locally, serve the repo root with any static file server and open `index.html` (paths in the HTML are root-relative, e.g. `assets/css/...`, `assets/js/...`):

```bash
python -m http.server 8080
```

`.claude/launch.json` already defines several named static-server configs (different ports) for use with the preview tooling — reuse one via the launch config rather than inventing a new port unless you need a guaranteed-uncached one (see caching note below).

To sanity-check the Phaser game file for syntax errors without a browser:
```bash
node --check assets/js/n5-phaser-game.js
```

There are no automated tests. Verification is done manually in a browser (see Preview/verification below).

## High-level architecture

### Two layers: OS shell + page content
`index.html` is a retro desktop UI (taskbar, start menu, draggable "windows") via `assets/js/{os,homepage,teleport,music-player,sakura,login,progress,study-progress,daily-quest,index}.js` and `assets/css/{os,homepage,navbar,components,animations,teleport,...}.css`. `assets/css/variables.css` is the single design-token source (colors, spacing, fonts, shadows) — check it before hand-picking new colors elsewhere. There is no boot/splash screen — that was removed (`boot.js`/`boot.css`/`#boot-screen` all deleted); `#login-screen` is the true entry point and shows directly.

**Auto-login, and why there's a script before `<head>`'s stylesheets finish loading**: a synchronous inline `<script>` at the very top of `<head>` checks `localStorage.jpExplorer` and adds `has-saved-explorer` to `<html>` *before first paint* — paired with `html.has-saved-explorer #login-screen{display:none}` / `#desktop{display:block}` in the inline `<style>` block right after it. This is what makes a "Home" link elsewhere in the app land directly on the desktop instead of flashing the login form first. `login.js`'s own `DOMContentLoaded` handler does the equivalent (`updateDesktop()` + swap display) redundantly, as a fallback for when `has-saved-explorer` wasn't set (e.g. localStorage unavailable) or to keep the two paths in sync — don't remove either half on its own. "Log Out" / "Switch Profile" in the Start menu (`.start-item.logout` / `.start-item.exit`) both just clear `jpExplorer` and reload; that's the *only* way back to the login form once a profile exists, so don't touch `initLogout()` in `login.js` without keeping some route back to login.

Content pages (JLPT levels, lessons, dashboards) live under `pages/<LEVEL>/...` and are separate HTML documents that pull in a subset of the same CSS/JS via relative paths (e.g. `pages/N5/n5-dashboard.html` uses `../../assets/css/...`). `templates/*.html` are starting-point templates for new lesson/quiz/mission/vocabulary pages, not live pages themselves.

Some files under `pages/` are stale/orphaned scratch copies with broken paths (e.g. `pages/N5/lesson-01-greetings.html` references `/css/style.css` and a Bootstrap-navbar structure that doesn't match the rest of the site) — don't treat everything under `pages/` as canonical without checking its `<link>`/`<script>` paths resolve. Likewise `dump.html` (an isolated HTML fragment, not a full document) and `klasjdlas.html` (a near-duplicate of `index.html`) at the repo root appear to be scratch/backup files rather than live entry points.

### Persistence: localStorage, one key per concern
No backend — all state lives in `localStorage`, each concern its own key, always wrapped in try/catch that degrades to an in-memory/no-op default rather than throwing (privacy mode, quota, corrupted JSON, etc. must never break the page):
- `jpExplorer` — the logged-in player profile/progress object (name, xp, streak, avatar, achievements); read/written in `login.js`/`progress.js` via `getSavedExplorer()`/`applyPlayerProgress()`.
- `jpLibraryOS.n5.favorites`, `jpLibraryOS.n5.avatarColor` — N5 dashboard state (`n5-save.js`, exposed as `window.N5Save`).
- `nekoBunko.n5.progress`, `nekoBunko.n5.catColor`, `nekoBunko.n5.quizGate`, `nekoBunko.n5.favorites` — Phaser game state, defined and loaded near the top of `n5-phaser-game.js` (`loadProgress`/`saveProgress`, `loadFavorites`/`saveFavorites`, etc.). Follow this exact pattern (key constant + try/catch load/save pair) for any new persisted state rather than reading/writing `localStorage` inline. `nekoBunko.n5.catColor` is also read (never written) by `assets/js/companion-cat.js` — see "Companion Cat" below — so the color picked once in the Adventure Room's `CatSelectScene` is what the sitewide companion shows everywhere else too.
- `nekoBunko.study.v1` — Study Room XP/lesson-completion store, `assets/js/study-progress.js` (`window.StudyProgress`). See the Study Room section below.
- `nekoBunko.dailyQuest.v1` — `{ date, lessonId }`, the homepage's "Today's Quest" pick for the current calendar day. See "Homepage desktop" below.
- `nekoBunko.streakPopup.v1` — `{ lastShownDate }`, the once-per-day gate for the streak check-in popup. See "Streak popup" below.

### The Phaser game (`assets/js/n5-phaser-game.js`)
Loaded only from `pages/N5/n5-dashboard.html`, after the `phaser@3.90.0` CDN script. Two scenes:
- `LibraryScene` — the main walkable map. Player moves via arrow keys or click-to-pathfind (`moveQueue`), auto-walks a waypoint corridor to reach clicked interactives, and everything except the outer walls/top wall-block is intentionally **non-solid** (shelves, decor, piles) so every interactive stays reachable — don't add solid bodies to decor without re-verifying reachability.
- `CatSelectScene` — the avatar/cat-color picker shown before the library loads. Its retro dark-panel `▶`-prefixed selection-list pattern (bg rect, gold title, tan/gold option text, keyboard nav with debounced up/down flags, click support) is the template the in-canvas shelf/review-pile menus (`openRetroMenu`/`buildRetroMenu`/`updateRetroMenuInput`) were built to match — reuse this exact visual/interaction pattern for any new in-canvas menu instead of inventing a new style or falling back to a DOM panel.

Key structural pieces:
- `LAYOUT` (near the top) is the single source of truth for all vertical/horizontal positions (shelf columns, row Y-coordinates, corridor/sofa/reception Y). Change layout here, not by hand-tuning coordinates scattered through `buildShelves()`/`buildFurniture()`.
- `ASSET_RECTS` holds pixel crop rectangles (`{x, y, w, h}`) used to cut individual sprites out of packed asset sheets (`assets/images/...`) at runtime via `cropToTexture(scene, sourceKey, rect, destKey)`. **When adding or fixing a crop, scan for opaque pixel runs per-row (or per-column), not with a single global bounding-box flood fill** — packed sheets place sprites close enough together that a bounding-box scan reliably merges neighbors into one crop. Every `destKey` passed to `cropToTexture` must be unique (Phaser throws on reuse).
- `LESSON_DATA` + `SHELF_PREREQ` define the 17 lessons/shelves and their unlock prerequisites — this is a simpler, purpose-built structure, not the more elaborate lesson schema described in `Neko-Bunko-Cat-Library-Spec.md` (that doc is an earlier design spec; treat it as historical intent, not as a description of the current data model).
- Interactives (shelves, review piles, the staircase quiz gate) share one click/keyboard entry path — `openInteraction(entry)` — which routes to either `openRetroMenu()` (shelves, review piles) or the older DOM `openPanel()` (currently only the final-quiz staircase panel). `refreshAllStates()` re-derives locked/available/completed visuals for every interactive from `this.progress`/`SHELF_PREREQ` after any state change; call it after any progress/favorite mutation instead of hand-updating individual sprites.

### The LessonBox dialogue component (`assets/js/lesson-box.js` + `assets/css/lesson-box.css`)
The only DOM-based UI in an otherwise canvas-drawn game — a retro JRPG-style dialogue overlay (`window.LessonBox.open(pages, options)` / `.advance()` / `.close()` / `.isOpen()`) invoked from `startLesson(entry)` in `n5-phaser-game.js`. Lesson content lives in `LESSON_CONTENT[shelfId]`, an array of typed "page" objects; each page's `type` picks a rendering branch in `renderContent()`: `greeting`, `sentence`, `conjugation`, `grammar-intro`, `summary`, `conversation`, `try-it`, `quiz-fill`, `quiz-review`, `quiz-answers`, `quiz-score`. The field contract for each type is documented in a comment block at the top of `renderContent()` — read it before adding a new page rather than guessing field names from examples.

**Review piles** (`review-1`..`review-4`, `BOOK_PILE_DATA`) work exactly like shelves as far as `LessonBox` is concerned: `openRetroMenu()`'s `hasContent` check is `!!LESSON_CONTENT[entry.id]` regardless of `entry.kind`, so a pile with a `LESSON_CONTENT` entry opens the dialogue via `startLesson()` just like a shelf does (piles just skip the shelf-only "Make Favorite?" option). Only `review-1` ("Foundations Review") is populated so far — piles without an entry still fall back to the old instant-complete behavior. Its structure is the template for the rest: an intro page, one recap page per gated shelf (reusing that shelf's real vocab/pattern data, not re-authored prose), then a **`quiz-review` → `quiz-answers` → `quiz-score` group**:
- `quiz-review`: mixed multiple-choice (`{kind:'mc', prompt, choices, correctIndex}`) and fill-in-the-blank (`{kind:'fill', prompt?, before, after, answer, altAnswers?}`) questions. Answers are captured into `state.quizReviewAnswers` (keyed by question index) as the player interacts — **no inline grading**, unlike `quiz-fill`.
- `quiz-answers`: reveals the correct answer next to what the player actually answered, grading via `gradeQuizQuestion()` against the **same `questions` array reference** the `quiz-review` page used (author both pages' `questions:` field pointing at one shared `const`, e.g. `REVIEW_1_QUIZ_QUESTIONS`, so they can't drift apart). Stashes `{correct, total}` into `state.quizReviewScore` as a side effect of rendering.
- `quiz-score`: reads `state.quizReviewScore` and shows the tally plus a retro-cat reaction line auto-picked by percentage via `quizScoreMessage()` in `lesson-box.js` (three tiers: <55%, 55-79%, 80-100%) — every `quiz-score` page gets this for free; only set `page.note` to override it for a specific lesson.

Global features apply automatically to every lesson (not per-page opt-in): an ambient open chime, a pulsing "spoken word" animation on word tiles, and a CRT power-on pop-in on `open()`.

**Per-player dynamic content** — some page fields can't be static because they depend on which cat color the player picked (there's no way to know that when `LESSON_CONTENT` is authored). The pattern: author the field as a **function** instead of a plain value, then resolve it once at lesson-open time in `startLesson()` before handing pages to `LessonBox.open()`:
- `conversation` pages' `turns[].spritePath` — resolved by `resolveConversationTurns(pages, playerColorId)`, which derives a `senseiColorId` distinct from the player's own color (falls back to black when the player picked orange, else orange) and looks up `ACTION_SPRITE_PATHS[action][colorId]`.
- `grammar-intro` pages' `diagramSvg` — normally a static HTML/SVG string, but can be a `(playerColorId, senseiColorId) => string` function instead (e.g. shelf-05's `buildDemonstrativesDiagram`); resolved by `resolveDynamicDiagrams(pages, playerColorId)` using the same sensei-color derivation. Pages with a static string `diagramSvg` pass through unchanged.

Follow this factory-function-plus-resolver pattern for any new field that needs to reflect the player's chosen color — don't hardcode a color or duplicate the sensei-color fallback logic inline.

**Visual aids on `greeting` pages** — `imageSrc`/`visualAlt` (a real photo/illustration) or `iconSvg` (raw inline SVG) render into the same framed slot, floated right so text wraps around it. For a vertically-stacked sprite sheet (multiple equal-height images in one file, e.g. a day/night strip), add `spriteRows`/`spriteIndex` alongside `imageSrc` instead of pre-cropping a separate file — it renders as a `background-image` with `background-size`/`background-position-y` computed to show just that one band (see `.lesson-box__greeting-visual--sprite` in `lesson-box.css`).

**Fonts — split by size, not one stack everywhere.** `.lesson-box-overlay`'s default font is a system monospace stack (`ui-monospace, Consolas, Menlo, ...` — no network dependency). VT323 (self-hosted at `assets/fonts/VT323-Regular.woff2`, `@font-face` in `lesson-box.css`; previously Google-Fonts-loaded, which silently fell back to a plain font whenever that request was slow/blocked) is only applied explicitly to "header or bigger" elements — kana display text, word tiles, big-idea/explain-text, takeaway, dialogue bubbles, quiz sentences/prompts/answer lines, the kana column of data tables. Small captions/hints/notes (romaji, pronunciation guides, gloss captions, "Your answer:" lines, table romaji/meaning columns) inherit the readable default — VT323's pixel shapes get muddy at caption sizes. When adding a new text element, default to the readable font (do nothing) and only add `font-family: "VT323", "DotGothic16", monospace;` explicitly if it's genuinely display-sized content. DotGothic16 (still Google-Fonts-loaded) covers Japanese characters in both stacks via automatic per-character fallback.

**Word-tile row alignment gotcha** — `.lesson-box__sentence-row` uses `align-items: flex-end`, so every `.lesson-box__word-tile` in a row must have the *same total height* or the shorter tile's kana text visibly shifts relative to its neighbors (not just a wrapping problem — a tile that's a few px shorter overall misaligns just as badly as one that wraps to 2 lines). For a tile whose gloss caption is unusually long (a whole phrase as one tile, e.g. よろしくお願いします), set `smallGloss: true` on that tile — it shrinks the caption to 11px, forces `white-space: nowrap` (the inherited 130px `max-width` would otherwise still wrap it even at the smaller size), and pins `line-height: 27px` (the exact height a normal 15px caption already renders at) so the tile's total height still matches its neighbors despite the smaller font.

### The Study Room — document mode (`assets/js/study-room.js` + dashboards)
A second, separate way to work through the N5 curriculum: plain HTML/CSS document pages instead of the Phaser canvas, reached via `pages/missions/levels-dashboard.html` → `pages/missions/n5-lessons.html` → `pages/missions/study-room.html?lesson=<id>`. Shares no code with `n5-phaser-game.js`/`lesson-box.js` — it's a from-scratch, simpler engine. Three lesson families, each with its own id namespace and its own `<optgroup>` in the picker:
- **30 grammar shelves** — `s01`, `s02`, `s02b`, `s02c`, `s03`..`s06`, `s07a`-`s07e`, `s08a`-`s08d`, `s09a`/`s09b`, `s10a`-`s10c`, `s11a`-`s11c`, `s12`..`s16` (30 total, not 18 — `s02b`/`s02c` already split shelf-02's content further than the Adventure Room does, and several later shelves got the same treatment, each per explicit feedback that the original bundled multiple distinct topics into one page: `s07` split into five — `s07a` Basic Numbers / `s07b` つ&人 Counters / `s07c` Telling Time / `s07d` Counters for Animals / `s07e` Counters for Things; `s08` split into four — `s08a` There Is/Are / `s08b` Direction Words / `s08c` Movement & The Compass / `s08d` Places — Common Locations; `s09` (Nouns & Pronouns) split into two — `s09a` Nouns / `s09b` Pronouns, since a noun and a pronoun are different word classes with different jobs; `s10` (Adjectives) split into three — `s10a` い-Adjectives / `s10b` な-Adjectives / `s10c` Adverbs, each expanded with real conjugation depth rather than just relocated, since cramming all three into one page was exactly what kept any of them from getting room to breathe; `s11` (Verbs) split into three — `s11a` Ichidan Verbs / `s11b` Godan Verbs / `s11c` Kuru & Suru (Irregular Verbs), each page ordered as its own N5 verb list first, then that group's ます-form conjugation pattern, with the one shared "verb basics" intro (three groups exist, を marks the object) living once, in `s11a`, rather than repeated on all three. None of these split groups keep a bare parent lesson of their own — each sub-lesson is a standalone object literal returned by its own `s0X()`/`s0Xa()` factory function. If a future shelf feels similarly overstuffed, split it the same way (new id suffix, own factory function, own entry in `buildLessons()`) rather than piling more `sections` into one lesson — but check whether the content genuinely divides into distinct sub-topics first, the same judgment call that drove every split so far.
- **1 kanji lesson** — `k01` (`kanjiGroup: true`), see the existing kanji bullets below.
- **3 checkpoint quizzes** — `cq1`/`cq2`/`cq3` (`quizGroup: true`), see the dedicated bullet below — added after the initial content-fidelity pass, one 10-question review roughly every 5 shelves in curriculum order (cq1: s01/s02/s02b/s02c/s03, cq2: s04/s05/s06/s07a-e/s08a-d, cq3: s09-s13; the last 3 shelves roll into the existing N5 Final Quiz instead of a cq4). Every split shelf that later landed inside one of these three spans (07/08 inside cq2, 09/10/11 inside cq3) kept the checkpoint boundary itself unmoved — only the number of lessons inside that span grew. `CQ2_QUESTIONS`'/`CQ3_QUESTIONS`' per-question `// sXX` comments were updated to the new sub-lesson ids each time a split landed inside their span (e.g. `CQ3_QUESTIONS`' あなた/こんな questions retagged `s09b`, its い-adjective/な-adjective questions retagged `s10a`/`s10b`, its 帰る/を questions retagged `s11b`/`s11a`) — the question CONTENT didn't need to change, just which id each one is tagged under.

- **Lesson selection**: a `<select id="studyLessonSelect">` in the page header (`renderLessonPicker()`/`highlightActiveLesson()`), not a sidebar list — deliberately, to leave the instruction panel full-width. Builds three `<optgroup>`s (shelves / N5 Kanji / Checkpoint Quizzes), routing each lesson via its `kanjiGroup`/`quizGroup` flag. `refreshLessonPickerLabels()` re-derives the ✓-prefix from `StudyProgress.isLessonDone()` after a lesson completes; don't hand-toggle a CSS class the way the old sidebar buttons did.
- **Draggable resize divider between the two panels (added 2026-09-03)** — `assets/js/study-panel-resize.js`, one shared self-initializing script loaded by *both* N5's `study-room.html` and N4's `study-room.html` (identical `.study-main`/`.study-instruction`/`.study-practice-col` markup in both, so one script covers both engines). A `.study-resize-handle` div sits between the two panels; dragging it sets `.study-instruction`'s inline `flex` to `0 1 <pct>%` (flex-shrink left *on*, not `0 0`, so `.study-practice-col`'s own `min-width:320px` can still claim space back on a narrower window instead of forcing an overflow), clamped 25–75%. No persistence — always resets to the CSS default 50/50 split on page load, per explicit decision. Hidden via `display:none` under the same `max-width:800px` media query that stacks `.study-main` into a column, with `flex-basis:auto !important` on `.study-instruction` there too, in case a resize happened at a wider viewport before the window was narrowed without a reload.
- **Font size scaled up 1.15x across `study-style.css` (added 2026-09-03)** — every one of the file's ~216 `font-size: Npx` declarations, including bespoke pixel-fitted diagram widgets (route maps, tile grids, compass diagrams), via a one-off Node script (not committed, same throwaway-script convention as `insert_samples.js`) rather than 216 hand-edits — flat multiplier chosen specifically to preserve the existing size hierarchy rather than flattening it. Applied per explicit request to bump *everything*, accepting the risk that some tightly-fitted diagram text could now wrap/overflow; no full visual sweep of every diagram has confirmed all of them still fit cleanly at the new sizes — if a specific diagram looks cramped, that's the likely cause, not a fresh bug.
- **`wordBank`**: each lesson declares a small object of categorized vocab (`{ subjects: [...], verbs: [...], ... }`, plain `{jp, en[, romaji]}` entries) — the *only* words that lesson's exercises are allowed to use. An optional `wordBank.preview` array holds 1-2 words/a particle borrowed from the *next* lesson (omitted on `s16`, the last one), rendered as a visually distinct "coming up" chip with a note + meaning via `buildWordBankBox()`. A parallel `wordBank.newWords` array (most shelves have one, 5 entries each — a noun/adjective mix real to that lesson's theme; the `s07a`/`s07b`/`s07c`/`s08a`/`s08b`/`s08c` split lessons have fewer, 1-3 each, since the original two shelves' 5-word pools got divided rather than expanded) is exposure-only the same way `preview` is — rendered as its own visually distinct "🆕 New this lesson" block (`.word-bank-box__new`, amber-adjacent but a different token so it doesn't get confused with the preview chips) and **never** wired into `buildWordBankExercises()`/grading.
- **`buildWordBankBox()` shows `newWords`/`preview` only, not the lesson's full category vocab** — it used to also loop every `wordBank` category (subjects/verbs/particles/etc, via now-deleted `WORD_BANK_LABELS`/`WORD_BANK_ROLES` lookup tables) into a "Fixed word bank for this lesson" listing, but that just repeated the same words the `vocab` table above it already showed. Cut per explicit feedback ("kinda redundant... to have the vocabulary, then phrases again"); the box title changed to plain "🔒 Word bank" and only renders the New/Preview blocks now. `buildWordBankExercises()`'s grading logic is untouched — it still draws from the lesson's full `wordBank` object regardless of what this box displays.
- **Exercise reference-word chips no longer show up front** — `renderExercise()` used to populate `#studyWordBankRef` with every exercise's `refWords` as non-clickable chips immediately, which meant the "exercise" was really just copying the shown words into the input box. Per explicit feedback ("remove the words in the exercise... let the user properly think things through"), `#studyWordBankRef` now stays empty at render time; `showHint()` is what populates it, and only once the learner has earned it via 2 wrong attempts (see the hint-gating bullet below) — and even then it shows the WORDS only (shuffled chips), not the full constructed sentence, so the learner still has to work out order/particles themselves.
- **`buildWordBankExercises()`**: returns 1-2 (occasionally 3) exercise objects (`{prompt, accepted, hint, refWords}`), slot-filling randomly from `this.wordBank` at call time — reuse the established `pick()`/`uPick()`-at-build-time pattern rather than inventing new randomization. `accepted` is an array of token-arrays; `checkAnswer()` joins and compares each one, so encode valid N5 variants (alternate particles, punctuation) as additional entries rather than special-casing grading logic. When a `wordBank.preview` word fits grammatically into the lesson's own established sentence pattern, add one more "bonus" exercise using it (prompt prefixed `(bonus — sneak peek: shelf N+1)`); when it doesn't fit cleanly, leave the preview exposure-only and say why in a comment — don't force a sentence that doesn't make sense just to use the word.
- **Three grading modes in `checkAnswer()`**, checked in this order — `ex.openEnded` first, then `ex.pattern`, then the original `ex.accepted` exact-match, so older exercises are unaffected by either newer mode:
  - `pattern` (a `RegExp`) grades by sentence *shape* instead of one baked-in word, so the learner can use any word from the word bank — including one carried over from an earlier lesson — instead of being marked wrong for not typing the one word `pick()` happened to choose. Only retrofitted onto exercises where any word choice is genuinely grammatical either way (s03's "A は B です", s05's demonstrative exercise) — **not** applied to exercises with a real grammatical noun/counter pairing (e.g. s07b's つ/匹 counters, where `wb.nouns[i]` is deliberately paired with `wb.counters[i]` and opening that up would let a student submit an ungrammatical pairing and have it marked correct).
  - `openEnded` (a free-write with no single correct answer, e.g. s04's jiko-shoukai capstone exercise) skips `accepted`/`pattern` entirely and calls `ex.validate(rawInput)` if present (falls back to "non-empty" otherwise) — s04's `validate` just checks for `です` present and a minimum length, since anything stricter would need real language understanding this engine doesn't have.
  - Both new modes still flow through the *same* attempts/hint/reveal machinery as the original exact-match mode (see next bullet) — they only change what counts as "correct," not the surrounding UI.
- **Hint button is gated behind 2 wrong attempts**, not shown immediately — `renderExercise()` now `hide()`s `studyHintBtn` at the start of every exercise, and `checkAnswer()`'s wrong-answer branch only `show()`s it once `attempts >= 2`. Applies to every word-bank exercise across all lessons (the 3-wrong-attempts auto-reveal-and-move-on behavior underneath is unchanged). `showHint()` itself reveals `ex.refWords` as chips into `#studyWordBankRef` (see the reference-chips bullet above) rather than the full `ex.hint` string — exercises without `refWords` (a few pattern/open-ended ones) fall back to the old full-hint text since there's no word list to show instead.
- **Kana-equivalent accepted answers**: real kanji in a graded `accepted`/`hint` only exists in three places in the whole file — s04's よろしくお願いします, and s15/s16 (静か/古い/本/好き/学生/先生/図書館/公園/勉強します/遊びます/猫/友達) — every other shelf's `accepted` was already pure kana. Each of those got a second, hiragana-only `accepted` entry alongside the kanji one (e.g. s16's `wordBank` entries gained a `kana:` field next to `jp:`, consumed in `buildWordBankExercises()`) so a learner who hasn't memorized that particular kanji yet can still answer correctly. If a future lesson introduces new kanji into a graded answer, apply the same pattern rather than requiring the kanji spelling only.
- **Furigana — built, `partial coverage by design`**: `annotateFurigana(text)` + the `KANJI_READINGS` dictionary (both near the top of `study-room.js`, above `buildLessons()`) scan a string and wrap every dictionary match in `<ruby>…<rt>…</rt></ruby>`, longest match first at each position (so a compound like `静かです` matches before the shorter `静か` would); anything not in the dictionary passes through untouched rather than erroring. Wired into `buildVocabTable()` and the `examples` loop in `renderInstruction()` — **not** into `hint`/hint-reveal text, which stays plain. Whole-word readings, not per-character (`静か` → one `しずか` `<rt>`, not two) — simpler to author correctly, at the cost of not being typographically "proper" ruby. `.vocab-table__jp rt`/`.example-sentence rt` in `study-style.css` keep `rt` on Space Mono (not VT323 — same "readable font at caption size" rule as everywhere else), with extra `line-height`/`padding-top` on the parent so the annotation has room above the base text. **This does not cover all of N5** — a full sweep of every `jp:` field in the file found **244 individual kanji characters** with no dictionary entry, spanning lessons (numbers, calendar/time, travel/places, family vocab, etc.) that weren't touched in the session that built this. ### Mondai worksheet — the per-lesson practice engine (replaced the old step-by-step quiz entirely)
Both N5's `study-room.js` and N4's `study-room-n4.js` present a lesson's practice section as a real JLPT-style もんだい (mondai/"problem set") worksheet — two labeled blocks, もんだい1 and もんだい2, of 5 multiple-choice questions each, **both shown on one sheet at once** (no gating divider between them), graded together on a single Submit. This is the SECOND practice engine this file has had: an earlier pass built a one-at-a-time fill-in-the-blank flow, then a "Quiz Set 2" word-order/★-slot rearrange exercise on top of it — both were removed wholesale per explicit feedback ("i don't like the word order rearrange quiz, i need this two mondai renshuu type of quiz for all lessons... displaying the mondai 1 5 questions and mondai 2, 5 questions in half right of the page") rather than layered further. If you see a stale reference to `currentExercises`/`renderExercise()`/`checkAnswer()`/word-order anywhere (a comment, an old memory note), it's describing this removed system — the code itself is gone from both files.
- **Rendering — `renderMondaiQuiz(lesson, container)`**, defined once per file (separate copies, same shape, since each file is its own IIFE with no shared scope — same N4/N5 pairing convention as everywhere else in this doc). Scoped to checkpoint quizzes only, per explicit decision — the regular mondai worksheet's `gradeAndShow()` still calls plain `renderXpBadges()`.

### Kana Dojo (`pages/missions/kana-dojo.html` + `assets/js/kana-{data,writer}.js`)
A third, separate practice mode: a hiragana/katakana stroke-order trainer, reached from Mission Hub. `kana-data.js` defines `window.HIRAGANA_STROKES`/`window.KATAKANA_STROKES` (46 characters each, `{char, romaji, row, strokes:[...]}`), and `kana-writer.js` is the generic renderer (`window.KanaWriter.init({chars, gridEl, viewerEl, svgEl, ...})`) that `kana-dojo.html`'s Hiragana/Katakana tab toggle re-points at whichever array is active via `writer.setChars(...)`.

- **Stroke data is real KanjiVG data, copied verbatim** — every `d` path string is taken as-is from KanjiVG's per-character SVG source (`https://github.com/KanjiVG/kanjivg`, `kanji/<codepoint-hex>.svg`), not hand-fit or re-smoothed. This is a deliberate replacement for an earlier hand-built dataset (RDP-simplified + custom quadratic-smoothed skeletons extracted from a different source) that looked visibly wrong on katakana's hard corners — KanjiVG is also what jisho.org's own stroke diagrams are built from, so matching that reference exactly was the actual point of switching. Because of this, the SVG viewBox is `0 0 109 109` (KanjiVG's native scale), **not** `0 0 100 100` — don't rescale the coordinates if you add more characters, just copy the path data straight from a fetched `kanji/<codepoint>.svg` and keep the 109 viewBox.
- **Animation technique**: each stroke is an SVG `<path>` with `stroke-dasharray`/`stroke-dashoffset` both set to `getTotalLength()`, then dashoffset transitions to 0 — the classic "line draws itself" trick. A faint full-character `.kana-writer__guide` outline (every stroke, static) renders first so the learner can see where the character is heading. Each stroke also gets a numbered dot at `getPointAtLength(0)` (never a hand-picked coordinate), fading in when its stroke starts and settling to a dim "done" state once it finishes.
- **The "Stroke order" strip** (`buildStrokeOrderStrip()` in `kana-writer.js`, styled in `study-style.css`) is a separate, static, jisho.org-style reference: one small boxed frame per stroke showing every earlier stroke gray/faint plus the new stroke solid black with a red start dot, ending in one full-size completed-character thumbnail with no box. This is intentionally *not* animated (no dash-offset trick) — it's meant to sit there as a look-back reference while the learner traces on paper, separate from the big animated viewer above it.

### Homepage desktop (`index.html` + `assets/css/homepage.css` + `assets/js/homepage.js`)
The desktop's windows (`#playerWindow`, `#discWindow`, `#questWindow`, `.journey-window`, `.footer-window`) are **all absolutely positioned with hand-tuned pixel offsets**, inside `.desktop-container` (`display:grid`, `grid-template-areas: "header" "row" "journey" "footer"`) — the grid areas exist but most windows opt out of grid flow via `position:absolute`/`fixed` and hard-coded `top`/`left`/`right`/`bottom` values instead. This is inherently fragile: changing one window's size can silently make another overlap it, since nothing is computed relative to actual sibling content. When repositioning anything here, **measure actual rendered `getBoundingClientRect()`s and check pairwise overlap** rather than reasoning about the CSS values alone — the layout has repeatedly not matched what the raw numbers suggested.

- **`position:fixed` on a grid-descendant did not respond to its own `bottom` offset** in this project's browser-preview tooling specifically (confirmed: changing the authored `bottom` value from 24px to 200px to 0px produced *zero* change in rendered position, even with `!important` and forced reflow; a plain test element appended directly to `<body>`, outside the grid, behaved correctly). `.journey-window` hit this and was switched to `position:absolute` + a measured `top` (matching the pattern every other desktop window already uses) instead of chasing the `fixed`+`bottom` combination further. If a future window needs bottom-anchoring here, prefer `position:absolute` + `top` computed from a sibling's actual rendered bottom edge over `position:fixed` + `bottom`.
- **JS-driven inline style mutations on `.retro-window` elements did not reflect in `getComputedStyle`/`getBoundingClientRect`** when set via the browser-preview tooling's JS execution (confirmed on both `#journeyWindow`'s `bottom` and `#playerWindow`'s `width`, with the inline `style` attribute correctly showing the new value but layout/computed-style not budging) — this is what the real drag-resize handles in `os.js` also do (`windowEl.style.width = ...`), so **simulating a drag-resize via injected JS in this preview tooling is not a reliable verification method for these elements**; a real interactive resize (or a real browser) is needed to confirm resize-dependent CSS (e.g. the player-card container queries below) actually works.
- `.player-card` (`#playerWindow`'s content) uses **CSS container queries** (`container-type: inline-size` + `cqw`-based `clamp()` for text/icon sizing, plus an `@container player-card (max-width: 190px)` breakpoint that collapses the 3-column stat grid to 1 column) so the avatar/icons/text shrink with the *window's own* resized size, not just the viewport — a plain `vw`/`rem` unit can't see that a single window got dragged smaller. - **Window buttons** (`.window-close`/`.window-minimize`/`.window-maximize`, wired in `os.js`'s `initializeWindowButtons()`) are matched by DOM position (`buttons[0]`/`[1]`/`[2]`), not by class — every `.window-buttons` block across the six desktop windows must keep them in close/minimize/maximize order or the click handlers attach to the wrong action. Close now actually hides the window (`display:none`, no animation) — it was a hardcoded no-op before; don't reintroduce a no-op close.

Press Start 2P was picked over VT323 after a side-by-side mockup.

A decorative `.scroll-title__cursor` block after the title blinks via the same `steps(1)` keyframe technique.
- **Hero cat, replacing the old logo image** (`.login-cat` in `login.css`, now a child of `.login-header`, sitting where `<img class="login-logo">` used to be — that `<img>` was removed from `index.html` entirely, and `.login-logo`'s CSS rule went dead with it) — this went through several iterations worth knowing about:
  - **Sprite — swapped repeatedly, expect it to keep changing**: currently `assets/images/avatars/whiteCatLick.png` (a lying-down, self-licking cat, 1536x64px, 24 frames), the *fourth* sprite tried here — first the sleep-loop sheet (sitting on the title bar, before this even replaced the logo), then `{color}CatPlaying.png`, then `Sprite-0002.png`, then `Sprite-0005.png`, now this. Each swap needs its own crop math computed fresh — **don't assume the previous sprite's numbers carry over** — via a direct pixel scan (a small Node script decoding the PNG's IDAT/scanline filters by hand, no library; confirms exact frame count, pitch, and per-frame content bounds). This same scan is also how a reported "moving sideways" bug on `Sprite-0005.png` got root-caused and fixed on the swap: a per-column opaque-pixel scan of `whiteCatLick.png` confirmed every frame's content run starts at a *constant* offset from the last (13, 77, 141, 205... — each exactly 64px apart), meaning the cat's body sits at the identical local position in every frame; `Sprite-0005.png` apparently lacked that constancy, which is what let the sitting cat visibly creep sideways as the animation cycled. Re-verify a new sheet's per-frame offsets the same way before trusting it not to drift. Two crop styles have come up so far depending on how tightly the sheet is packed:
    - **Sheets with real dead space around each frame** (`Sprite-0002.png`'s 705x65/11-frame sheet, content only ~36x40 of each ~64px cell) need literal-px crop math: a fixed local x/y offset within the cell, scaled to a target display height, with `background-position`'s "from"/"to" keyframe values computed as `-(frameOffset*cellPitch + localOffset) * scale`. Skipping this and using the naive full-cell crop is the literal cause of an early "huge gap above the cat" bug report (on the very first sleep-loop version).
    - **Sheets where content already fills nearly the whole cell** (`Sprite-0005.png`'s 480x32/15-frame sheet, and now `whiteCatLick.png`'s 1536x64/24-frame sheet — both exact-pitch, content spanning ~2px-to-cell-edge) don't need that — the plain percentage-based `background-position` trick (0%→100%, `background-size` set to `frameCount*100%` — 2400% for the current 24-frame sheet — same technique `companion-cat.css` uses for its multi-sheet animations) is both simpler and resolution-independent, since no per-breakpoint px recompute is needed for a smaller mobile size the way the literal-px version required. The container stayed a plain square (source cells are square, 64x64 for the current sheet) with `margin-bottom` pulled 5px tighter (`-11px`, was `-6px`) so the cat visually nestles against the title text below it rather than floating with a gap.
  - **Color is theme-aware via CSS `filter`, not a separate source image**: none of these sprites came with a black/white sibling export the way the sitewide companion-cat sheets do, so `.login-cat--black`/`.login-cat--white` (added by `login-cat.js`'s `applyCatColor()`, same effective-theme logic as `companion-cat.js`'s `isDarkTheme()` — explicit `nekoBunko.theme` wins, else `prefers-color-scheme`) apply `grayscale(1) brightness(<factor>)` to whatever the one source image is instead of switching `background-image`. A deliberate approximation (a multiplicative `brightness()` can't fully flatten near-zero outline pixels to zero, so linework stays visible either direction) — the exact brightness factors are tuned per sprite's own base tone (a lighter-toned source needs a smaller "white" factor than a saturated one) and are not guaranteed to look right if copied onto a future sprite swap without re-checking. If a real black/white export of the current sheet ever shows up, prefer swapping the source image back over keeping the filter hack.
  - **Deliberately ignores `prefers-reduced-motion`** — every other animation on this site respects it, this one doesn't, by explicit user decision after confirming their system has it enabled and still wanting the loop to play. Worth knowing why this matters here specifically: the `{color}CatPlaying.png` sprite (a pouncing/reaching pose, no longer used) looked broken when frozen under reduced motion — its static frame 0 read as two disconnected cat-shaped blobs, which is what got reported as a "duplicate cat" bug before a live console check traced it to `animationName` genuinely computing to `"none"` (only one `.login-cat` element ever existed, not two). Both sprites used since then have every frame at a similar, compact, centered size, so neither has that failure mode — but if a *future* sprite swap ever reintroduces an extended/dynamic pose, re-check how its frame 0 looks completely still before assuming reduced-motion support can just be re-added with a bare `animation:none`.
  - **Title-scramble effect**: also in `login-cat.js` — periodically dissolves `.scroll-title__text` ("Welcome to Neko Bunko OS") into random katakana and resolves it back left-to-right (`Math.floor((i/len) * SCRAMBLE_STEPS)` per-character reveal frame), on its own independent timer loosely synced with nothing in particular — it just reads as connected because both are "the cat is playing" motion happening at once.
  - **Debugging note**: this project's browser-preview tooling reports `prefers-reduced-motion: reduce` as permanently true and `document.hidden` as permanently true, in every tab, regardless of the real OS setting — confirmed while chasing the bug above. Don't trust an animation-related finding from this tooling alone; verify computed `animationName`/`animationDuration` values instead of expecting a visual screenshot to show motion.
  - **Historical**: the original resting-cat version (sleep-sheet, sitting on the title bar, not yet replacing the logo) hit an asset gotcha worth remembering if a similar `.ase`-only asset ever needs extracting again — the requested `OrangeCatLogin` asset only existed as `assets/images/avatars/OrangeCatLogin.ase`, and the `ase-parser@0.0.18` npm package silently returned empty layers/cels for it despite the file being valid (raw-byte chunk dumping confirmed real Layer/Cel chunks present). Worked around by hand-parsing the Cel chunk directly (header: `layerIndex:u16, x:i16, y:i16, opacity:u8, celType:u16`, then for `celType===2` a `w:u16, h:u16` pair + zlib-compressed RGBA). Turned out unnecessary — the decoded sprite was pixel-identical to `orangecat-sleep-sheet.png`, already sitting in the repo as a proper PNG — but the technique is worth reusing if a genuinely PNG-less `.ase` ever needs decoding for real.

### Companion Cat (`assets/js/companion-cat.js` + `assets/css/companion-cat.css`)
A small ambient idle-sprite widget that follows the player across every page **except** the Adventure Room and the N3/N4 Phaser maps (those already have their own in-scene cat/Neko-sensei presence — the companion would just be a redundant second cat there, so it's deliberately not wired into `n5-dashboard.html`/`n3-dashboard.html`/`n4-dashboard.html`). Self-initializing: `<script src=".../companion-cat.js">` on a page is all that's needed, it builds and appends its own DOM on `DOMContentLoaded`, no markup required in the page body.

- **Identity**: reads `nekoBunko.n5.catColor` (the same key the Adventure Room's `CatSelectScene` writes) — it's meant to be *your* cat, not a separate character. **Dark-mode override**: `getCatColor()` shows white regardless of the saved color whenever the effective theme is dark (white reads far better than orange/black against a dark backdrop) — checked via the same `nekoBunko.theme` key the homepage's taskbar toggle writes (`"light"`/`"dark"` wins outright; otherwise falls back to `prefers-color-scheme`). This widget runs on pages that don't have that toggle's UI at all, which is exactly why it reads the shared `localStorage` key/media query directly instead of depending on `os.js`.
- **Visibility**: only renders once `localStorage.jpExplorer` exists — stays hidden on the login screen.
- **Sprite**: idles on `assets/images/avatars/{color}CatTailWagging.png`, not the `{color}CatIdle.png` walk-cycle sheets used elsewhere (those read as "mid-stride," wrong for a cat sitting still in a corner). The three color sheets share one clean, evenly-pitched 64px-per-frame grid (verified by decoding the raw PNG pixel data — there's no Aseprite JSON export alongside them) — if any of these sprite sheets get re-exported, re-verify the pitch is still uniform before assuming a plain `steps(5)` animation will still look right.
- **Ambient extra actions**: on top of the idle tail-wag loop, `scheduleNextAction()` in `companion-cat.js` fires an occasional "scratching" or "playing" burst at a random 16-34s gap (`EXTRA_ACTIONS`), swapping to `{color}CatScratching.png`/`{color}CatPlaying.png` for a few frames via `.is-scratching`/`.is-playing` classes (companion-cat.css), then back to idle — this replaced an earlier "standing"/"playing" pair after a request to cycle through Scratching/TailWagging/Playing specifically. `{color}CatPlaying.png` sheets are trimmed exports with non-uniform per-frame widths (unlike TailWagging) — companion-cat.css handles that with percentage-based `background-position` (0%→100%) so `steps(N)` alone determines frame count regardless of the sheet's exact pixel width, rather than needing per-sheet crop math.
  - **`{orange,white}CatScratching.png` are NOT simple trimmed strips — they're real 8-column x 2-row GRIDS** at the same 64px cell pitch idle already uses, confirmed by a per-row (not just per-column) opaque-pixel scan finding two distinct 32px-tall row-runs 64px apart. A first pass only scanned columns, miscounted this as "8 frames," and applied the plain single-row percentage trick — which squashed both rows into the container's height at once, rendering as two overlapping cats. Fixed by pinning `background-position-y` to the top row (`0%`) and doubling `background-size`'s height (`200%`, i.e. one row = 100% of the container) so only row 1's 8 real frames ever show; row 2 is currently unused (unconfirmed whether it's packing padding or a redundant duplicate). **Lesson worth repeating**: when a "sheets where content fills the cell" percentage-crop sheet turns out to look wrong once applied, re-scan it for ROWS as well as columns before assuming the frame count alone was the only unknown.
  - **Real asset gap, not a bug**: `blackCatStandingUp.png`/`.ase` and `blackCatScratching.png`/`.ase` are byte-identical (confirmed via hash) to `blackCatTailWagging.png`/`.ase` — no distinct "standing up" or "scratching" pose was ever exported for the black cat (and `blackCatScratching.png` is a plain single-row 5-frame sheet like TailWagging, not a 2-row grid like the other colors' scratching sheets — it's literally the same file, not just a similar pose). `EXTRA_ACTIONS.black` still lists `"scratching"` alongside `"playing"` for parity with the other two colors, but a black cat's scratching burst will just silently replay its own idle frames until a real sheet gets exported.
- **Placement**: fixed bottom-right everywhere, **except** `index.html` specifically, where `body:has(#desktop) .companion-cat` pushes it up to `bottom:172px` (was `160px`; bumped +12px when the taskbar grew from 34px to 46px — see the taskbar bullet above) — homepage.css's own `.footer-window` and os.css's full-width `.taskbar` both live in that same corner, and the plain bottom-right offset was measured to collide with them. Also guards against ever showing alongside `#login-screen`'s own `.login-cat` (checks `getComputedStyle(loginScreen).display !== "none"` before rendering) in case the auto-login hide-logic doesn't fire before this widget's own `DOMContentLoaded` check runs.

### Streak popup (`assets/js/streak-popup.js` + `assets/css/streak-popup.css`)
A once-per-day "you're on an N-day streak" check-in overlay, self-initializing like Companion Cat. Reuses `jpExplorer.streak` (the homepage Player window's own streak field via `applyPlayerProgress()`) rather than a parallel counter. Gated to once/day via `nekoBunko.streakPopup.v1`'s `lastShownDate`, but fires from *any* of three triggers, not just page load: a `DOMContentLoaded` listener, and a `"nekoBunko:studyProgress"` DOM event that `study-progress.js`'s `completeLesson()`/`recordQuizRun()` dispatch on every call (regardless of whether XP was actually gained) — `study-progress.js` doesn't need to know `streak-popup.js` exists, it just dispatches the event unconditionally, and `maybeShow()` (exposed as `window.StreakPopup.maybeShow`) no-ops if today's popup already fired. This is the general pattern for "something happened, some unrelated widget might care" in this codebase — a broadcast event, not a direct function-call dependency.

**Real bug, now fixed**: the popup overlay is appended straight to `document.body`, which sits *outside* `.study-room.is-terminal` in the DOM — but its CSS used bare `var(--term-panel)`/`var(--term-border)`/etc. with no fallback, and those custom properties are only ever defined *inside* `.study-room.is-terminal`. A custom property with no matching ancestor resolves to nothing, so the popup rendered with missing/wrong colors — invisible or unreadable, not obviously "broken." Fixed by giving every `var()` in `streak-popup.css` an explicit literal fallback (`var(--term-panel, #032821)`, etc.) rather than relying on DOM placement to supply them. **This is a recurring bug class in this codebase** — the same fix shape was needed for `.conv-hl`/diagram colors ported into Study Room from `lesson-box.css` (see the Study Room section above) and is worth checking for any time a component gets moved to, or its markup copied into, a different DOM subtree than the one its CSS custom properties were authored against.

### Preview/verification workflow gotcha
The dev "server" is just static file serving, but the browser preview tooling can serve **stale JS even after a hard reload** once a port has been used once in a session — when verifying a code change actually took effect, prefer starting the preview on a port/launch-config that hasn't been used yet in the current session rather than trusting a reload on a reused port.

**Resize/reload ordering also matters for this tooling specifically**: calling the viewport-resize tool *after* a page has already loaded/animated, then reading layout immediately, has produced measurements that don't match the actual CSS (e.g. a `width:380px` rule reading back as `1428px`). The reliable sequence confirmed by repeated testing: resize the viewport **first**, *then* navigate/reload, *then* measure — never resize mid-session on an already-loaded page and trust the next immediate reading. If a measurement looks physically impossible (an element wider than its explicit CSS `width`, a `position:fixed` element's rect not moving when its CSS offset changes), suspect this ordering issue or the inline-style-mutation issue above before concluding the site's CSS is wrong.

**`requestAnimationFrame` does not fire while the preview tab reports `document.hidden === true`** — confirmed directly (an rAF callback registered right after a click simply never ran; `document.visibilityState` read back `"hidden"` even after explicitly fronting the tab). This preview session's Browser pane apparently doesn't always count as "visible" to the page's own paint scheduler. Any code that needs to force-reflow-then-animate should race `requestAnimationFrame` against a short `setTimeout` fallback rather than depending on rAF alone — confirmed and fixed in `kanji-cards.js`'s `afterReflow()` helper (a `done` guard flag, `requestAnimationFrame(run)` and `setTimeout(run, 50)` both racing to call the same callback; see the FLIP-zoom description above). `kana-writer.js`'s stroke-draw playback uses a bare double-nested `requestAnimationFrame` with no such fallback and predates this finding — it hasn't been verified against this specific failure mode, so don't assume it's already safe if you touch it. This matters for real users too, not just this tool — a backgrounded tab suspends rAF the same way, so the fallback is a genuine robustness fix, not a test-only workaround.

**A newly-created element's `getBoundingClientRect()`/`getComputedStyle()`/`offsetWidth` can disagree with its own inline `style` attribute after a JS-driven mutation** — this generalizes the `.retro-window` finding above (which was specific to homepage windows) to *any* dynamically-created, `position:fixed` element resized via JS a tick after creation: confirmed on `kanji-cards.js`'s modal card mid-build, where `element.getAttribute("style")` correctly showed the just-set target `width/height/top/left`, but every layout-reading API (`getBoundingClientRect`, `getComputedStyle`, `offsetWidth`) reported completely different, smaller numbers that didn't correspond to any value the code ever set — reading the element back to compute a *second* animation step (e.g. "where is the card centered right now, so I can compute where the detail panel goes next to it") silently used garbage input as a result. **The fix, not just a workaround**: don't read a just-mutated element's rect back at all — if the target geometry is deterministic (computable from `window.innerWidth`/`innerHeight` alone, as a centered-and-sized layout always is), recompute it with the same formula instead of trusting a DOM readback. This is both the reliable fix for this tool and better practice generally, since it removes a whole class of readback-timing races.
